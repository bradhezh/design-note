---
title: 1.3. Decorators, Reflection, and Metaprogramming
---

In the previous section, signals were shown to wire up customisers in GUI frameworks, where each slot must connect to a sender from which the signal is emitted, because signals with the same name but from different instances must be handled individually. For example, two buttons trigger entirely different business workflows.

In web backends, by contrast, there is no concept of distinct instances emitting requests, meaning that handlers do not need to differentiate any instances to connect to, but simply specify which route to handle. Note that route patterns are determined at compile time and then can be generated by compilers. This implies that if languages support compile-time metadata generation and runtime reflection, routes for wiring-up can be expressed as declarative annotations generating metadata on handlers. Frameworks can then reflect those metadata to wire handlers up, wherever frameworks determine, such as the route table. These annotations are known as attributes in C# or decorators in general, introducing metaprogramming — instructing compilers to generate metadata and even source code programmatically.

Furthermore, web backend applications are inherently stateless. Request-specific data is managed by frameworks, allowing frameworks to take full ownership of instances. With metadata for classes, methods, and decorators, frameworks instantiate objects, resolve their graphs, manage their lifecycles, inject them into handlers, and wire everything up for customisation. This is known as Inversion of Control (IoC) or Dependency Injection (DI). Consequently, applications can be written as pure classes decorated with metadata, shifting from imperative code logic to declarative data descriptions.

Modern compilers push metaprogramming further through compile-time source code generation. Frameworks leverage source generators such as Roslyn in C# to inspect decorators during compilation and generate source code with metadata hardcoded as constants. This approach eliminates runtime reflection, facilitating native Ahead-of-Time (AOT) compilation for languages on virtual machines such as C# and Java to improve runtime performance. Metaprogramming with source generation actually enables code to serve as policies, as compilers make higher-order code vary at compile time.

Declarative elegance does not imply a rejection of the imperative style, which retains advantages of directness, conciseness, and performance. Indeed, ASP.NET adopts imperative Minimal APIs as its recommended default starting point. Minimal APIs use delegates (like signals) to wire up handlers imperatively instead of relying on declarative attributes, while still leveraging DI for backend instance management. It also supports route groups to organise related handlers (endpoints) under shared routing and request-processing behaviour. Furthermore, both approaches can coexist within the same application, with Minimal APIs for rapid initial development, while introducing attributes and controller classes when certain pipelines are required.

```cs title="Program.cs"
namespace CtlrDemo;

using CtlrDemo.Hello;

public class Program {
  public static void Main(string[] args) {
    // For DI (builder.Services), configs (builder.Configuration, appsettings.json, ...), logging
    // providers (builder.Logging, ILogger), the web host (builder.WebHost) and env
    // (builder.Environment), ...
    var builder = WebApplication.CreateBuilder(args);
    builder.Services.AddTransient<IHelloService, HelloService>();
    // Controllers are actually created for each request via DefaultControllerActivator, mainly for
    // performance, while still with dependencies for DI to manage. To register controllers
    // themselves to DI, use builder.Services.AddControllers().AddControllersAsServices(), which
    // registers them transient by default.
    builder.Services.AddControllers();
    // Build all into the app
    var app = builder.Build();

    // Wire up the controllers with attribute routing
    app.MapControllers();

    app.Run();
  }
}
```

```cs title="Hello/Controller.cs"
namespace CtlrDemo.Hello;

// Actually, all public, non-generic, non-abstract, and non-static classes with the "Controller"
// suffix or [Controller] (or derived from one with [Controller], like ControllerBase) are
// controllers.
// For API features like automatic validation and param inference, requiring attribute routing
[ApiController]
// For attribute routing. Without attributes for routing, controllers should still be wired up
// imperatively like:
// app.MapControllerRoute(name: "default", pattern: "{controller=Home}/{action=Index}/{id?}");
// which wires up controllers according to their class and method names.
[Route("[controller]")]
public class HelloController(IHelloService helloService): ControllerBase {
  // Can also be used for attribute routing
  [HttpGet]
  public IActionResult Hello() {
    return Ok(helloService.Hello());
  }
}
```

```cs title="Hello/Service.cs"
namespace CtlrDemo.Hello;

public interface IHelloService {
  string Hello();
}

public class HelloService: IHelloService {
  public string Hello() => "Hello, Controllers!";
}
```

### Minimal APIs in ASP.NET

```cs title="Program.cs"
using Minimal.Hello;

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddTransient<IHelloService, HelloService>();
var app = builder.Build();

app.MapHelloEndpoints();

app.Run();
```

```cs title="Hello/Endpoints.cs"
namespace Minimal.Hello;

public static class HelloEndpoints {
  // `this` on the 1st param makes it (a static method in a static class) an extension method for
  // IEndpointRouteBuilder
  public static IEndpointRouteBuilder MapHelloEndpoints(this IEndpointRouteBuilder app) {
    var group = app.MapGroup("/hello");

    group.MapGet("/", (IHelloService helloService) => {
      return Results.Text(helloService.Hello());
    });

    return app;
  }
}
```

C# GUI frameworks typically provide events and commands for wiring-up, while with XAML supported via reflection or metaprogramming for applications to declaratively describe UI components and wiring-up. Events encapsulate delegates for UI components, and commands implement a standard interface for methods to be wired up in XAML. GUI applications can also leverage DI to hand over instance management of certain classes. Note that DI works on metadata and resolves instances via types, providing standard management such as singleton and transient modes. This implies that DI cannot concurrently manage two distinct instances (e.g. buttons) of the same class with different states (e.g. labels and positions), and UI components are typically managed by XAML.

GUI applications typically adopt a classic Model-View-Controller (MVC) architecture to decompose logic into separate layers, where controllers handle UI events, call business logic provided by models, and update the UI accordingly. Consequently, UI logic is in views and controllers, while models are decoupled from any UI related operations. Furthermore, introducing UI states can decompose UI logic into rendering and interaction, where controllers update UI states instead of direct UI operations. As a result, controllers are also decoupled form UI operations and only responsible for interaction logic, leaving all UI operations isolated in views. This is known as Model–View–ViewModel (MVVM) in .NET GUI.

```cs title="App.axaml.cs"
using Ava.Views;
using Ava.ViewModels;
using Ava.Hello;

namespace Ava;

public partial class App: Application {
  public override void Initialize() { AvaloniaXamlLoader.Load(this); }

  public override void OnFrameworkInitializationCompleted() {
    if (ApplicationLifetime is IClassicDesktopStyleApplicationLifetime desktop) {
      //desktop.MainWindow = new MainWindow { DataContext = new MainViewModel() };
      // Only use DI for models and view-models, not for views because they are typically
      // instantiated with XAML (requiring param-less constructors) or possibly by ViewLocator
      var services = new ServiceCollection()
        .AddSingleton<IHelloService, HelloService>()
        .AddSingleton<MainViewModel>().BuildServiceProvider();
      desktop.MainWindow =
        new MainWindow { DataContext = services.GetRequiredService<MainViewModel>() };
      desktop.Exit += (_, _) => services.Dispose();
    }
    base.OnFrameworkInitializationCompleted();
  }
}
```

```cs title="ViewModels/MainViewModel.cs"
using Ava.Hello;

namespace Ava.ViewModels;

public partial class MainViewModel(IHelloService helloService): ViewModelBase {
  // Generate code for the PropertyChanged event, which will be triggered on the property changes.
  // Although views can get these properties and update controls for PropertyChanged in app-specific
  // ways, with XAML binding, views can work in a universal way, via either reflection
  // (ReflectionBinding) or source generation (CompileBinding, as the default in Avalonia 12).
  [ObservableProperty]
  public partial string Message { get; set; } = "";
  [ObservableProperty]
  public partial string CommandText { get; set; } = "Greet";

  // Generate code for a command property with the method name and "Command" suffix (ToggleCommand
  // here), and with the method as its action. Commands implement a standard interface (ICommand)
  // for XAML binding, supporting CanExecute and CanExecuteChanged out of the box.
  [RelayCommand]
  private void Toggle() {
    if (string.IsNullOrEmpty(Message)) {
      Message = helloService.Hello();
      CommandText = "Clear";
    } else {
      Message = "";
      CommandText = "Greet";
    }
  }
}
```

```c title="main.c"
#include <gtk/gtk.h>

#include "controllers/main.h"

#define GTK_APP_ON_ACTIVATE "activate"

int main(int argc, char *argv[]) {
  GtkApplication *app = gtk_application_new("gtk.demo", G_APPLICATION_DEFAULT_FLAGS);

  g_signal_connect(app, GTK_APP_ON_ACTIVATE, G_CALLBACK(on_app_activate), NULL);
  int status = g_application_run(G_APPLICATION(app), argc, argv);

  g_object_unref(app);
  return status;
}
```

```c title="controllers/main.c"
#include <gtk/gtk.h>

#include "controllers/main.h"
#include "hello/service.h"

#define GTK_BTN_ON_CLICKED "clicked"

static void on_toggle_clicked(GtkButton *toggle, gpointer editable) {
  g_return_if_fail(toggle && editable);
  GtkEditable *message = GTK_EDITABLE(editable);

  if (!g_strcmp0(gtk_editable_get_text(message), "")) {
    gtk_editable_set_text(message, hello());
    gtk_button_set_label(toggle, "Clear");
  } else {
    gtk_editable_set_text(message, "");
    gtk_button_set_label(toggle, "Greet");
  }
}

void on_app_activate(GtkApplication *app, gpointer user_data) {
  g_return_if_fail(app);
  // GtkBuilder won't take ownership of windows and widgets, and windows (with contained widgets)
  // should be destroyed via gtk_window_destroy instead of ref counts. By default, GTK also destroys
  // windows on the "close-request" signal (e.g. the close button being clicked).
  GtkBuilder *builder = gtk_builder_new_from_resource("/gtk/demo/main.ui");
  GtkWindow *window = GTK_WINDOW(gtk_builder_get_object(builder, "window"));
  GtkEntry *message = GTK_ENTRY(gtk_builder_get_object(builder, "message"));
  GtkButton *toggle = GTK_BUTTON(gtk_builder_get_object(builder, "toggle"));

  gtk_window_set_application(window, app);
  g_signal_connect(toggle, GTK_BTN_ON_CLICKED, G_CALLBACK(on_toggle_clicked), message);
  gtk_window_present(window);

  g_object_unref(builder);
}
```
